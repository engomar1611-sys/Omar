# المعمارية المقترحة — NEW FEED ERP

## 1. المبادئ
- Modular Monolith في البداية لتقليل تعقيد التشغيل، مع حدود نطاق واضحة تسمح بفصل خدمات لاحقاً عند الحاجة.
- PostgreSQL مصدر البيانات المركزي.
- واجهات API موثقة بين تطبيق Windows والويب والخادم.
- منطق الأعمال والتحقق والترحيل المالي والمخزني في طبقة الخادم، وليس في الواجهة.
- كل مستند له دورة حالة واضحة: مسودة، مرسل للاعتماد، معتمد، مرحّل، ملغى/معكوس وفق ضوابط.

## 2. مكونات الحل
1. Web UI: واجهة عربية RTL للمتصفح.
2. Windows Client: تطبيق موظفين يتصل بالخادم عبر HTTPS ويعرض حالة الاتصال والإصدار.
3. Backend API: المصادقة، الصلاحيات، قواعد الأعمال، المستندات، التقارير.
4. PostgreSQL: البيانات التشغيلية والمالية وسجل التدقيق.
5. File Storage: مرفقات المستندات وشهادات الجودة والنسخ الاحتياطية في مساحة منفصلة.
6. Background Worker: مهام التقارير الثقيلة، التنبيهات، النسخ الاحتياطي والتحقق من التحديثات.
7. Reverse Proxy / TLS: إنهاء TLS وإدارة الشهادات وفق بيئة النشر.

## 3. تقسيم نطاقات الخادم
- Identity & Access
- Master Data
- Procurement
- Inventory & Batch Tracking
- Formulation & Nutrition
- Production & Planning
- Quality Management
- Sales & Distribution
- Finance & Accounting
- Cost Accounting
- Maintenance
- HR (حسب النطاق المعتمد)
- Reporting & Audit

## 4. قواعد البيانات
- مفاتيح أساسية UUID أو BIGINT وفق قرار التنفيذ.
- استخدام NUMERIC للدقة المالية والكميات التي تتطلب كسوراً؛ يمنع استخدام floating point للأموال.
- تخزين الوقت بتوقيت موحد مع عرض التوقيت المحلي.
- قيود FK وUNIQUE وCHECK، وفهارس على رقم المستند والتاريخ والصنف والتشغيلة.
- ترحيل الحركات من خلال معاملات ذرية مع منع التكرار idempotency.
- حفظ نسخة التركيبة ومواصفاتها داخل مرجع أمر الإنتاج لضمان ثبات التاريخ.

## 5. الأمن
- HTTPS فقط في الإنتاج.
- كلمات مرور مخزنة بتجزئة قوية، جلسات قصيرة العمر وتجديد آمن.
- صلاحيات أقل امتيازاً، وتحقق من الصلاحية على الخادم لكل طلب.
- سجل تدقيق للأحداث الحساسة.
- أسرار الاتصال والشهادات خارج المستودع.
- لا تُرفع بيانات إنتاج أو كلمات مرور أو مفاتيح خاصة إلى Git.
- نسخ احتياطي مشفر واختبار استعادة دوري.
- تحديثات Windows موقعة والتحقق من سلامة الحزم قبل التطبيق.

## 6. النشر والتعافي
- خادم رئيسي، مع تصميم احتياطي يحدد لاحقاً: standby/replication أو backup-and-restore حسب الميزانية وRPO/RTO.
- بيئات منفصلة للتطوير والاختبار والإنتاج.
- مراقبة مساحة القرص، قاعدة البيانات، الخدمة، الشهادات، والنسخ الاحتياطية.
- خطة rollback للتطبيق وقاعدة البيانات، مع migrations متوافقة قدر الإمكان.

## 7. ملاحظات تنفيذية
هذه وثيقة معمارية مبدئية وليست إثباتاً لوجود كود أو خادم منشور. اختيار إطار Backend وWindows UI وأدوات النشر يتم بعد اعتماد خطة التنفيذ والقيود التقنية.
