# حزمة تشغيل واختبار NEW FEED ERP على Windows

## ما الذي تتضمنه الحزمة؟

- واجهة Web عربية RTL تعمل من المتصفح.
- Backend API على Node.js 22 داخل Docker.
- PostgreSQL 16 مع تخزين دائم.
- ترحيل تلقائي لإصدارات قاعدة البيانات عند تشغيل خدمة API.
- إنشاء أول مدير نظام من PowerShell.
- سكربتات نسخ احتياطي واستعادة لقاعدة الاختبار.

**حدود مهمة:** هذه نسخة Web/API للاختبار على Windows باستخدام Docker Desktop. لا تتضمن حتى الآن برنامج Windows مستقلًا بصيغة EXE/MSI، ولا إعداد HTTPS إنتاجيًا أو تحديثًا رقميًا موقعًا. لا تستخدمها على بيانات إنتاج حقيقية.

## المتطلبات

- Windows 10/11 أو Windows Server مع Docker Engine/Compose v2 مدعومين.
- Docker Desktop أو Docker Engine مع Docker Compose v2.
- اتصال إنترنت أول مرة لسحب Node 22 وPostgreSQL 16.
- المنفذ 3000 متاح (يمكن تغييره).

## التشغيل لأول مرة

1. فك نسخة المستودع أو افتح مجلد المشروع.
2. افتح PowerShell داخل مجلد المشروع.
3. نفّذ:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start-test.ps1
```

السكربت ينشئ ملف `.env` محليًا بمفاتيح عشوائية إذا لم يكن موجودًا، ويبني الخدمات ويشغل PostgreSQL وAPI، ثم يسألك عن إنشاء أول مدير. كلمة المرور لا تقل عن 14 حرفًا ولا تُحفظ في المستودع.

افتح `http://localhost:3000`، وسجل الدخول. من جهاز آخر داخل الشبكة استخدم `http://IP-الخادم:3000` بعد السماح بالمنفذ في Windows Firewall. لا تفتح المنفذ للإنترنت العام.

لتغيير المنفذ شغّل `scripts/start-test.ps1 -Port 3100` عند إنشاء ملف البيئة لأول مرة، أو عدّل `APP_PORT` في `.env` ثم أعد التشغيل:

```powershell
docker compose up -d
```

## فحوصات سريعة

```powershell
Invoke-RestMethod http://localhost:3000/health
Invoke-RestMethod http://localhost:3000/ready
docker compose ps
docker compose logs --tail 100 api
```

المتوقع أن تكون حالة `/health` هي `ok` وحالة `/ready` هي `ready` مع اتصال قاعدة البيانات.

## النسخ الاحتياطي والاستعادة

نسخة SQL نصية:

```powershell
.\scripts\backup-test-db.ps1
```

استعادة نسخة اختبار (تمسح قاعدة الاختبار الحالية بالكامل بعد كتابة RESTORE):

```powershell
.\scripts\restore-test-db.ps1 -BackupFile .\backups\NEW-FEED-YYYYMMDD-HHMMSS.sql
```

اختبر الاستعادة على قاعدة منفصلة قبل الاعتماد على أي نسخة احتياطية. لا تستخدم سكربت الاستعادة على بيانات إنتاج.

## إيقاف وتشغيل

```powershell
docker compose stop
docker compose start
docker compose down
```

لا تستخدم `docker compose down -v` إلا إذا كنت تريد حذف بيانات قاعدة الاختبار نهائيًا.

## ما يجب اختباره قبل قبول النسخة

1. إعداد البيانات الأساسية: أنواع الأعلاف، المنتجات، الوحدات، الأصناف، الموردون، العملاء، المخزن.
2. طلب شراء داخلي → اعتماد → أمر شراء → استلام → فحص جودة؛ تأكد أن المقبول فقط يدخل المخزون.
3. تركيبة جديدة → إرسال للمراجعة → اعتماد مجموع 100%.
4. أمر إنتاج → صرف FEFO → تسجيل الناتج → فحص المنتج النهائي والإفراج عنه.
5. تسجيل هالك → عدم خصم المخزون قبل الاعتماد → اعتماد → تحقق من حركة المخزون والقيد.
6. فاتورة بيع → تسليم جزئي/نهائي → تحصيل وتخصيص → مرتجع واعتماد المخزن والحسابات والجودة.
7. سند صرف مورد ومرتجع مشتريات وفترة محاسبية مفتوحة/مغلقة.
8. راجع ميزان المراجعة وتقييم المخزون وتكلفة الإنتاج وتنبيهات الصلاحية.
9. اختبر مستخدمين وصلاحيات مختلفة، ومحاولات دخول خاطئة.
10. أنشئ نسخة احتياطية ثم استعدها على بيئة اختبار منفصلة.

سجل رقم الإصدار، المستخدم، الوقت، الخطوات، النتيجة، وصورة/سجل الخطأ لكل حالة.

## حدود الاعتماد

نجاح GitHub CI يثبت نجاح اختبارات الكود وترحيلات PostgreSQL داخل بيئة CI، لكنه لا يثبت تجربة المستخدم على أجهزة المصنع أو الطابعات أو الميزان أو الشبكة المحلية. يلزم تنفيذ سيناريوهات القبول أعلاه مع ممثلين من المشتريات والمخزن والجودة والإنتاج والمبيعات والحسابات قبل التشغيل الفعلي.
