# نشر HTTPS إنتاجي لـ NEW FEED ERP على Windows Server

## لماذا هذا الإعداد؟
خدمة API تستمع محلياً على 127.0.0.1 فقط. لا ينبغي أن يتصل بها جهاز الموظف مباشرة عبر HTTP. يتولى Caddy استقبال HTTPS على 443 وإنهاء TLS ثم تمرير الطلبات محلياً إلى API.

## قبل التنفيذ
1. احجز اسماً DNS ثابتاً مثل erp.company-domain.com واجعل سجل A/AAAA يشير إلى عنوان السيرفر الصحيح.
2. اسمح بالوصول الوارد إلى TCP 80 و443 على Windows Firewall والراوتر/الجدار الخارجي حسب سياسة الشبكة.
3. لا تفتح منفذ API الداخلي (3000 افتراضياً) على الشبكة.
4. ثبّت Caddy من مصدره الرسمي المعتمد داخل بيئة الشركة، وشغّله كخدمة Windows تحت حساب خدمة محدود الصلاحيات.
5. انسخ ReverseProxy.Caddyfile إلى مسار إعداد Caddy، واستبدل erp.example.com باسم DNS الفعلي.
6. إذا غُيّر منفذ API في إعداد المثبت، عدّل عنوان reverse_proxy في Caddyfile إلى 127.0.0.1 والمنفذ نفسه.
7. شغّل/أعد تشغيل خدمة Caddy، وتحقق من إصدار الشهادة وتجديدها وسجلات الخدمة.

## اختبار القبول
- من السيرفر: `Invoke-WebRequest http://127.0.0.1:3000/ready` يجب أن يعيد `status=ready` و`database=connected`.
- من جهاز آخر: `https://erp.company-domain.com/ready` يجب أن ينجح دون تحذير شهادة.
- من جهاز آخر: محاولة الاتصال بـ `http://SERVER-IP:3000/ready` يجب أن تفشل؛ API مربوط على loopback ولا يُفتح في الجدار الناري.
- تطبيق الموظفين يُضبط على عنوان HTTPS باسم DNS، وليس عنوان IP أو HTTP.
- اختبر انقطاع Caddy وعودة الخدمة وتجديد الشهادة قبل اعتماد الإنتاج.

## ملاحظات أمنية
- لا تستخدم شهادة ذاتية التوقيع في الإنتاج ولا تتجاوز تحذيرات TLS.
- لا تضع مفاتيح TLS الخاصة في المستودع.
- اسم DNS العام أو الداخلي يجب أن يكون قابلاً للحل من جميع أجهزة الموظفين.
- إذا كانت الخدمة داخل شبكة مغلقة دون DNS عام، استخدم PKI مؤسسية وشهادة صادرة من CA موثوقة وموزعة على أجهزة Windows بواسطة سياسة المؤسسة؛ لا تستخدم Caddy ACME العام لأسماء غير عامة.
- هذا الدليل قالب إعداد؛ لا يثبت أن DNS أو NAT أو شهادة الإنتاج قد أُعدت في شبكة العميل.
