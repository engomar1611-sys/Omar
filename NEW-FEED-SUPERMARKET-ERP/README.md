# NEW FEED SUPERMARKET ERP

مشروع نظام تشغيل وإدارة سوبرماركت متكامل، يُعاد تأسيسه من الصفر داخل هذا المجلد.

## القرارات المعتمدة
- واجهات عربية RTL مع دعم الإنجليزية، والعملة الأساسية EGP.
- لا يوجد موديول تقارير أو شاشات تقارير.
- نقطة بيع متعددة الكاشيرات، ومشتريات ومخازن وحسابات وعملاء وموردون وموظفون وأصول وتوصيل ومتجر إلكتروني وتطبيقات.
- دعم المنتجات المباعة بالوزن والوحدات والتحويلات وباركود الميزان وملصقات الباركود.
- متوسط تكلفة مرجح، وصرف FEFO للأصناف ذات الصلاحية، ومنع المخزون السالب وبيع الأصناف المنتهية.
- المرتجعات تمر بفحص المخزن ثم الاعتماد المالي قبل إعادة الصنف للمخزون المتاح أو رد المبلغ.
- لا تُختلق أسعار أو أرصدة أو باركودات أو أوزان تجارية. تُستورد من مصدر موثوق أو تُدخل وتُعتمد.

## بنية البداية المرفوعة
- `package.json`: إعدادات الحزم وأوامر التشغيل.
- `apps/api/src/server.js`: خادم API ونقطتا فحص التطبيق وقاعدة البيانات.
- `database/schema.sql`: نواة مخطط PostgreSQL للهوية والمنتجات والوحدات والباركود والمخزون والمشتريات والمبيعات والمدفوعات والحسابات.
- `.env.example`: إعدادات تشغيل نموذجية دون أسرار.

## التشغيل المحلي
1. تثبيت Node.js 20 أو أحدث وPostgreSQL.
2. نسخ `.env.example` إلى `.env` وتعديل بيانات الاتصال.
3. إنشاء قاعدة البيانات وضبط `DATABASE_URL` و`JWT_SECRET` و`BOOTSTRAP_SECRET` في `.env`.
4. تشغيل `npm install` ثم `npm run migrate` لتطبيق `schema.sql` والترحيلات 002 إلى 010 بالترتيب مرة واحدة.
5. تشغيل `npm run dev` ثم فتح عنوان الخادم `/` وإنشاء أول مدير من شاشة التهيئة.
5. فحص `GET /api/health` و`GET /api/health/database`، وفتح واجهة النظام من عنوان الخادم `/`.

## الحالة الحالية وحدود التحقق
تم رفع نواة المصدر الأولى إلى GitHub. هذه ليست نسخة مكتملة أو جاهزة للإنتاج. تم إنشاء واجهة أولية لنقطة البيع والتنقل بين الوحدات. بيانات المنتجات الظاهرة في شاشة العرض أمثلة غير حقيقية ولا تُرحّل إلى قاعدة البيانات. شاشات بقية الموديولات ما زالت هياكل أولية وليست عمليات مكتملة. لم تُنفذ بعد المصادقة، الصلاحيات الفعلية، سير العمل الكامل، الترحيلات، الطباعة، مزامنة العمل دون اتصال أو اختبارات الأجهزة. لم يتم حتى الآن تشغيل التطبيق أو تطبيق مخطط PostgreSQL على خادم اختبار؛ لذلك لا ندّعي نجاح اختبارات تشغيلية.

## كتالوج المنتجات والأسعار والباركود
- ترقيم داخلي تلقائي للأصناف بصيغة NF-00000001 وما بعدها، منفصل عن GTIN/EAN الرسمي.
- بيانات العلامات التجارية والشركات المصنعة وبلد المنشأ.
- تعريف حجم العبوة ووحدة العبوة والوحدة الأساسية، مع دعم الوزن والصلاحية.
- سجل تاريخي لأسعار الشراء والتجزئة والجملة والعروض، مع مصدر السعر وتاريخ رصده والمنطقة.
- إنشاء باركود داخلي Code 128، والاحتفاظ بالباركود الأصلي عند توفره من العبوة أو المورد.
- صفحة طباعة ملصق للصنف تتضمن الاسم والكود والباركود والسعر المسجل.
- قالب الاستيراد: `import-templates/products-eg.csv`.
- ملفات الترحيل الجديدة: `003_product_catalog_pricing.sql` ثم `004_barcode_sequence.sql` ثم `005_base_units_categories.sql`.

### مصادر بيانات السوق
يمكن تجهيز الاستيراد والتحقق من قوائم متاجر مصرية مثل Carrefour Egypt وSpinneys Egypt، ومقارنة الأسعار من Fattuta. لا يعني ذلك أن قاعدة بيانات جميع منتجات مصر أو تغطية كل الفروع والأسعار اللحظية قد تم استيرادها. الأسعار يجب أن تحتفظ بالمصدر والمنطقة وتاريخ الرصد، وأن تتم مراجعتها قبل اعتمادها كسعر بيع في الفرع.

### استيراد كتالوج المنتجات - API
- `POST /api/product-imports`: يستقبل دفعة JSON بحد أقصى 1000 صف، ويتحقق من التصنيفات والوحدات والحقول الأساسية، ثم يحفظها في منطقة مراجعة دون إنشاء منتجات تشغيلية أو اعتماد أسعار.
- `GET /api/product-imports/:id`: يعرض تفاصيل الدفعة والأخطاء لكل صف.
- يجب أن يحتوي كل صف على `name_ar` و`category_code` و`base_unit_code`. الحقول الاختيارية تشمل `brand_code` و`pack_size` و`pack_unit_code` و`is_weighted` و`tracks_expiry` و`manufacturer_barcode` و`retail_price` و`purchase_price` ومصدر السعر وتاريخ رصده.
- الاستيراد الحالي مرحلة تجهيز ومراجعة فقط؛ لا توجد بعد عملية اعتماد نهائي أو استيراد جماعي إلى كتالوج البيع، ولا يوجد ربط آلي حي بواجهات المتاجر.
- مثال جسم الطلب:
```json
{
  "source_name": "Supplier catalog - sample",
  "source_url": null,
  "rows": [
    {
      "name_ar": "اسم منتج موثق",
      "category_code": "BEVERAGES",
      "base_unit_code": "PCS",
      "brand_code": "BRAND-CODE",
      "pack_size": 1.5,
      "pack_unit_code": "L",
      "is_weighted": false,
      "tracks_expiry": true,
      "manufacturer_barcode": "barcode-from-package",
      "retail_price": 0,
      "purchase_price": 0
    }
  ]
}
```

## شاشة إدارة الأصناف والباركود
- شاشة الأصناف تستدعي `GET /api/products` من قاعدة البيانات وتعرض كود الصنف والاسم والتصنيف والوحدة والوزن والصلاحية.
- شاشة إضافة الصنف تستدعي القوائم المرجعية للتصنيفات والوحدات والماركات، ثم تحفظ عبر `POST /api/products`. ترك كود الصنف فارغًا يطلب توليد كود NF تلقائيًا.
- يمكن تسجيل باركود المصنع ضمن عملية إنشاء الصنف، أو توليد باركود داخلي من شاشة الأصناف.
- الطباعة تتيح المقاسات 30x20 و50x30 و70x40 و100x50 مم. الطباعة تعتمد على متصفح الجهاز ومكتبة JsBarcode المحملة من CDN؛ يلزم اختبار الطابعة الفعلية وضبط تعريفها وهوامشها قبل اعتمادها.
- شاشة استيراد الكتالوج تستدعي API مرحلة المراجعة فقط؛ لا يوجد حتى الآن زر اعتماد نهائي أو عملية ترحيل الصفوف المعتمدة إلى المنتجات والأسعار.

### اعتماد دفعات الكتالوج
- `POST /api/product-imports/:id/approve` يعتمد دفعة بحالة `review` داخل معاملة قاعدة بيانات واحدة.
- ينشئ الأصناف الصالحة ويربط التصنيف والوحدة والماركة، ويولد كود NF عند عدم توفير SKU.
- يحفظ باركود العبوة وأسعار الشراء والتجزئة والجملة المرسلة مع مصدر السعر وتاريخ الرصد.
- الصفوف التي تفشل مراجعها أثناء الاعتماد تتحول إلى rejected.
- شاشة استيراد الأصناف تعرض زر الاعتماد بعد نجاح الفحص.
- لا يوجد حتى الآن استيراد آلي حي من مواقع التجزئة أو جلب أسعار مباشرة؛ يلزم توفير ملفات موردين أو مصادر بيانات مصرح بها.

### ضبط استلام المشتريات
- عند استلام أمر الشراء، يتحقق النظام من أن الصنف ضمن بنود الأمر وأن الكمية لا تتجاوز المتبقي بعد خصم الاستلامات السابقة المعتمدة.
- يمنع الاستلام الزائد حتى عند تنفيذ استلامات جزئية متتابعة.
- بعد تسجيل الاستلام تظل حالة الأمر `part_received` حتى ينتهي فحص الجودة؛ ولا تتحول إلى `received` إلا بعد اعتماد الكميات المطلوبة.
- التحقق يتم داخل معاملة قاعدة البيانات مع قفل أمر الشراء لمنع التزامن على الأمر نفسه.
- ما زال مطلوبًا استكمال فحص الجودة، واعتماد قبول/رفض الاستلام، وربط تكلفة المخزون ومتوسط التكلفة المرجح والقيود المحاسبية قبل اعتبار دورة المشتريات مكتملة.

## موديولات التشغيل المضافة في الدفعة الحالية
ملف الترحيل `database/006_operational_modules.sql` يضيف جداول تشغيلية للموردين والعملاء الموسعة، وفحص استلام المشتريات، ومرتجعات البيع، والخزائن وحركات النقدية، والموظفين والورديات، والأصول والصيانة، والتوصيل، وطلبات التجارة الإلكترونية، والفترات المحاسبية والحسابات البنكية.

ملف `apps/api/src/routes/operations.js` يضيف واجهات API لقراءة وإضافة الموردين والعملاء والموظفين والأصول، وعرض أرصدة التشغيلات وحركات المخزون، وإنشاء طلبات التوصيل وتحديث حالتها، واستقبال طلبات المتجر الإلكتروني، وإنشاء الفترات المحاسبية وإغلاقها. تم تحميل المسارات في خادم API.

### حدود هذه الدفعة
هذه بنية تشغيلية وواجهات API أولية وليست اعتمادًا نهائيًا لكل الموديولات. لم يتم بعد استكمال دورة البيع POS وحجز/صرف FEFO والتحصيل والقيود المحاسبية، ولا سير موافقات المرتجعات والاستلام والفحص وربطها بمخزون قابل للبيع، ولا إدارة البنوك والتسويات والرواتب والإهلاك. كما لم يتم تشغيل PostgreSQL أو تنفيذ اختبارات تكامل فعلية في هذه البيئة. لا تعتبر النسخة جاهزة للإنتاج قبل تطبيق الترحيلات وتشغيل الاختبارات على قاعدة اختبار.


## Warehouse quality gate (migration 007)

Purchase receipts now enter `pending_inspection`. Received quantities are quarantined in non-saleable lots with zero saleable on-hand quantity. The warehouse inspection endpoint is:

- `POST /api/purchase-receipts/:id/inspect`
- Request body: `{ "inspected_by": "<user-uuid>", "lines": [{ "receipt_line_id": "<uuid>", "accepted_quantity": 8, "rejected_quantity": 2 }] }`
- Every receipt line must be submitted exactly once; accepted plus rejected quantity must equal the received quantity.
- Only accepted quantities become saleable stock and create inbound stock movements. Rejected quantities remain excluded from saleable inventory.
- POS and the inventory availability view filter out quarantined/non-saleable lots.

Apply `database/007_purchase_quality_workflow.sql` after the earlier schema migrations. This change has been committed to the repository, but has not yet been executed against a live PostgreSQL database. The receiving/inspection API still requires integration tests against the actual schema and user permissions before production use.


## تصحيح الاستلام وإدارة مرتجعات البيع (المهاجرتان 007 و008)

- تم تصحيح إنشاء لوط الاستلام ليستخدم تكلفة الوحدة الصحيحة دون تمرير معاملات SQL زائدة.
- لم تعد عملية الاستلام تنشئ حركة مخزون وهمية؛ حركة الوارد تُنشأ فقط بعد اعتماد فحص المخزن.
- أمر الشراء يظل قيد الاستلام الجزئي إلى أن يعتمد الفحص الكميات المقبولة. الكميات المرفوضة لا تُحتسب كرصيد متاح، ويمكن استبدالها باستلام لاحق.
- فحص الاستلام يجب أن يشمل كل سطر مرة واحدة، ومجموع المقبول والمرفوض يجب أن يساوي الكمية المستلمة.
- دورة مرتجع البيع أصبحت: طلب مرتجع مرتبط بسطور فاتورة مكتملة، ثم فحص مخزني، ثم اعتماد مالي، ثم تسجيل رد المبلغ.
- يمنع النظام رد كمية تتجاوز صافي الكمية المباعة بعد خصم المرتجعات السابقة غير المرفوضة.
- الأصناف المرتجعة بحالة تالفة أو منتهية لا تعود للمخزون. الصنف المقبول للبيع فقط يُنشأ له لوط جديد وحركة وارد بعد الاعتماد المالي.
- الأصناف التي تتبع الصلاحية تتطلب إدخال تاريخ صلاحية صالح عند قبولها للبيع.
- مسارات المرتجعات:
  - `POST /api/sales/:saleId/returns` لإنشاء طلب.
  - `POST /api/sales/returns/:id/inspect` لفحص المخزن.
  - `POST /api/sales/returns/:id/approve` للاعتماد المالي وإرجاع المقبول فقط للمخزون.
  - `POST /api/sales/returns/:id/refund` لتسجيل رد المبلغ بعد الاعتماد.
  - `GET /api/sales/returns` لعرض الطلبات.
- يجب تطبيق `database/008_sales_returns_workflow.sql` بعد `database/007_purchase_quality_workflow.sql`، ثم `database/009_backfill_legacy_receipts.sql` مرة واحدة أثناء الترقية وقبل فتح API الاستلام للمستخدمين، ثم `database/010_security_and_pos_defaults.sql`. الترتيب الكامل: `schema.sql` ثم 002 إلى 010.

**حدود التنفيذ:** تسجيل رد المبلغ يحفظ وسيلة الدفع والمرجع والمبلغ في سجل مستقل، لكنه لا ينشئ حتى الآن قيدًا محاسبيًا عامًا أو حركة بنك/خزينة تلقائية. كذلك لم تُنفذ اختبارات قاعدة بيانات حية أو اختبارات أجهزة POS والطابعات في هذه البيئة. لا تعتبر هذه الدورة معتمدة للإنتاج قبل استكمال ربط الأستاذ العام واختبارها على PostgreSQL.


### ترقية بيانات الاستلام القديمة
الترحيل `database/009_backfill_legacy_receipts.sql` يميز الاستلامات التي كانت معتمدة قبل إضافة بوابة فحص الجودة، ويحول كمياتها القديمة إلى كميات مقبولة ويحافظ على صلاحية التشغيلات الموجودة. يجب تشغيله مرة واحدة في نافذة الترقية قبل استقبال مستندات جديدة عبر API؛ لا تعِد تشغيله بعد بدء عمليات الاستلام الجديدة دون مراجعة أثره على البيانات.


## تسجيل الدخول والصلاحيات الأولية

- واجهة النظام تعرض شاشة تسجيل دخول، ولا تُرسل طلبات الموديولات إلا مع رمز جلسة صالح.
- أول مدير نظام يُنشأ مرة واحدة فقط عبر `POST /api/auth/bootstrap`؛ لا يوجد تسجيل مستخدمين عام.
- يجب ضبط `JWT_SECRET` بطول 32 حرفًا على الأقل و`BOOTSTRAP_SECRET` بطول 24 حرفًا على الأقل في إعدادات الخادم قبل التهيئة.
- طلب التهيئة الأول يحتوي `bootstrap_secret` و`username` و`display_name` و`password` (12 حرفًا على الأقل). بعد إنشاء المدير، يتم إغلاق مسار التهيئة تلقائيًا لأن قاعدة البيانات لم تعد فارغة.
- تسجيل الدخول عبر `POST /api/auth/login`. رمز الجلسة صالح لمدة 8 ساعات، وتُعاد شاشة الدخول عند رفض الرمز.
- الترحيل `010_security_and_pos_defaults.sql` يضيف الأدوار والصلاحيات الأساسية وطرق الدفع القياسية، ويربط جميع الصلاحيات بدور `SUPER_ADMIN`.
- طبقة API تطبق التحقق من الجلسة وصلاحية الموديول على المسارات التشغيلية. ما زال مطلوبًا بناء شاشة إدارة المستخدمين وتوزيع الأدوار والصلاحيات التفصيلية وربط الصلاحيات على مستوى كل إجراء حساس، مع اختبارها على قاعدة فعلية.

### التحقق الآلي
أضيف GitHub Actions workflow لفحص صياغة ملفات JavaScript باستخدام `npm run check` عند تغيير مجلد المشروع. هذا فحص صياغة فقط، وليس اختبار تكامل PostgreSQL أو اختبارًا بصريًا/فعليًا لأجهزة الكاشير والطابعات والماسحات.


## ربط شاشة الكاشير بقاعدة البيانات

- أزيلت قائمة المنتجات التجريبية الثابتة من شاشة POS؛ وتُحمّل الأصناف من `GET /api/products` مع السعر النشط والباركود المسجل.
- تُحمّل طرق الدفع والفرع الرئيسي والمستخدم الحالي من `GET /api/pos/context`.
- عند إتمام البيع ترسل الشاشة سطور الفاتورة إلى `POST /api/sales/complete`؛ ويتم اعتماد الكاشير من جلسة الدخول، وليس من قيمة يرسلها المتصفح.
- المنتجات التي لا تملك سعر تجزئة نشطًا لا يمكن إضافتها للبيع. كما يرفض الخادم البيع عند عدم كفاية المخزون القابل للبيع أو وجود صلاحية منتهية.
- الأصناف الوزنية تسمح بإدخال كمية عشرية حسب الوحدة الأساسية. لا يزال مطلوبًا استكمال تفسير باركود الميزان المشفر واختبار ميزان وطابعة فعلية.
- أضيف الفرع والمخزن الافتراضيان `MAIN` في الترحيل 010، دون إنشاء أصناف أو أسعار أو أرصدة افتراضية.

**حدود نقطة البيع:** البيع يسجل الفاتورة وحركات صرف المخزون والتحصيل داخل معاملة واحدة، لكنه لا ينشئ بعد قيود الأستاذ العام أو تسوية الخزينة/البنك تلقائيًا. يلزم استكمال المحاسبة قبل اعتماد البيع تشغيليًا.


### إدارة مخطط قاعدة البيانات
يستخدم المشروع `npm run migrate` لتطبيق `database/schema.sql` ثم ملفات الترحيل الرقمية بالترتيب، مع تسجيل كل ملف في جدول `schema_migrations` حتى لا يُعاد تطبيقه. خذ نسخة احتياطية قبل أي ترقية إنتاجية، وراجع خصوصًا الترحيل 009 لأنه يرحّل الاستلامات القديمة إلى حالة مقبولة مرة واحدة.
