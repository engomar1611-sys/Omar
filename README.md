# NEW FEED ERP

نظام ERP صناعي متكامل لإدارة مصانع الأعلاف، مصمم لدعم أنواع متعددة من الأعلاف وليس أعلاف الدواجن فقط.

## نطاق النظام المعتمد مبدئياً

- مصنع واحد وخط إنتاج واحد في المرحلة الأولى.
- 10–30 مستخدماً.
- واجهات عربية، مع دعم الجنيه المصري كعملة افتراضية قابلة للضبط.
- تطبيق Windows + واجهة Web + خادم مركزي.
- قاعدة بيانات PostgreSQL.
- أنواع أعلاف ديناميكية قابلة للإضافة، مثل أعلاف الدواجن والمواشي والأبقار والأسماك والأغنام والماعز.
- تركيبات مستقلة وإصدارات معتمدة ومواصفات جودة لكل منتج.
- إدارة المشتريات والمخازن والتشغيلات والإنتاج والجودة والمبيعات والحسابات والتكاليف والصيانة والتقارير.
- تتبع كامل للخامات والتشغيلات والمنتجات النهائية (Batch Traceability).
- صلاحيات حسب الدور، موافقات، وسجل تدقيق.
- HTTPS، نسخ احتياطي واستعادة، وتحديثات آمنة.

## دورة التشغيل الرئيسية

المشتريات والاستلام ← فحص الخامات ← اعتماد التركيبة ← أمر الإنتاج وصرف الخامات ← التصنيع ← فحص المنتج النهائي ← التخزين ← البيع والتسليم ← التحصيل والقيود والتكاليف.

## مبدأ التصميم

أنواع الأعلاف والمنتجات والتركيبات ومواصفات الجودة ليست قيماً ثابتة داخل الكود؛ بل بيانات قابلة للإدارة من النظام. ويجب أن تكون كل حركة مخزون أو إنتاج أو مالية مرتبطة بمستند مصدر واضح، مع دعم العكس المحاسبي والمخزني وفق الصلاحيات.

## حالة المشروع الحالية

يوجد Backend وواجهة Web عربية تغطي المشتريات والاستلام والجودة والمخزون والتركيبات والإنتاج والهالك والمبيعات والتسليم والتحصيل والمرتجعات والحسابات والتقارير والموارد البشرية والصيانة والإعدادات. توجد اختبارات Node.js وتكامل PostgreSQL 16 في GitHub Actions.

**حدود النسخة:** هذه ليست بعد نسخة إنتاج نهائية، ولا يوجد حالياً مثبت Windows مستقل EXE/MSI أو HTTPS إنتاجي أو تحديثات موقعة أو إثبات اختبار الطابعات والأجهزة الفعلية. توجد حزمة تشغيل واختبار Web/API على Windows عبر Docker في `docs/TEST_DEPLOYMENT.md`. راجع `docs/IMPLEMENTATION_STATUS.md` لقائمة المنفذ والمتبقي.


## تشغيل API لأول مرة (بيئة تطوير)

1. انسخ `backend/.env.example` إلى `backend/.env`، واضبط `DATABASE_URL` وأنشئ قيمة عشوائية قوية لـ `AUTH_JWT_SECRET` بطول 32 حرفاً على الأقل.
2. شغّل PostgreSQL، ثم من مجلد `backend` نفّذ `npm install` وبعدها `npm run migrate`.
3. لإنشاء أول مدير نظام فقط، عيّن متغيرات البيئة المؤقتة `BOOTSTRAP_ADMIN_USERNAME` و`BOOTSTRAP_ADMIN_NAME` و`BOOTSTRAP_ADMIN_PASSWORD` (كلمة مرور لا تقل عن 14 حرفاً)، ثم نفّذ `npm run bootstrap:admin`.
4. احذف متغير كلمة المرور المؤقت من البيئة بعد الإنشاء، ثم شغّل `npm start`.

أداة إنشاء المدير الأول ترفض العمل إذا كان هناك أي مستخدم موجود، وتمنح الدور الأول جميع الصلاحيات المسجلة وقت الإنشاء. لا تضع كلمات المرور أو مفاتيح JWT في Git أو ملفات مشاركة.

## واجهات API المنفذة مبدئياً

- الموردون: `GET/POST /api/v1/suppliers`.
- المشتريات: `GET/POST /api/v1/purchases`، واعتماد الأمر عبر `POST /api/v1/purchases/:id/approve`.
- الاستلام: `GET/POST /api/v1/goods-receipts`، واعتماد فحص الاستلام عبر `POST /api/v1/goods-receipts/:id/quality`.
- المخزون: `GET /api/v1/inventory/balances`.
- الإنتاج: `GET/POST /api/v1/production/orders`، تحرير الأمر عبر `POST /api/v1/production/orders/:id/release`، والإتمام عبر `POST /api/v1/production/orders/:id/complete`.
- جميع المسارات التشغيلية محمية بالمصادقة والصلاحيات. لا يُضاف المخزون من الاستلام إلا بعد اعتماد فحص الجودة.

## ملاحظة تكلفة المخزون والإنتاج

يُحدّث الاستلام متوسط تكلفة المخزون المرجح. وعند إتمام أمر التشغيل تُصرف الخامات من أرصدة التشغيلات المتاحة وفق الأقرب انتهاءً (FEFO)، وتُسجل تكلفة الاستهلاك الفعلية وتُحسب تكلفة وحدة المنتج النهائي من إجمالي تكلفة الخامات. لا تشمل هذه المرحلة بعد تكلفة العمالة والطاقة والهالك والتكاليف الصناعية غير المباشرة.


## المرحلة التجارية والمحاسبية التالية

أضيفت نواة APIs للعملاء وفواتير البيع والتحصيل الجزئي وتوزيع المقبوضات على الفواتير، والمرتجعات بموافقتين منفصلتين (المخزن ثم الحسابات)، والمصروفات، ودليل حسابات ابتدائي وقيود مزدوجة متوازنة. كما أضيفت مكونات تكلفة تشغيل (أجور، طاقة، مصروفات صناعية، تعبئة، هالك).

المسارات الرئيسية:
- `GET/POST /api/v1/customers`
- `GET/POST /api/v1/sales/invoices` (ترحيل الفاتورة وخصم المخزون والقيد المحاسبي ضمن معاملة واحدة)
- `POST /api/v1/accounting/receipts` (تحصيل وتخصيص كامل قيمة السند على فاتورة أو أكثر)
- `POST /api/v1/sales/returns`
- `POST /api/v1/sales/returns/:id/warehouse-approve`
- `POST /api/v1/sales/returns/:id/accounting-approve` (إضافة المخزون بعد الاعتمادين)
- `POST /api/v1/accounting/expenses`
- `GET /api/v1/accounting/journals`
- `POST /api/v1/production/orders/:id/cost-components`

هذه واجهات خدمة خلفية وليست شاشات مستخدم جاهزة. ما زالت هناك حاجة إلى اختبارات تكامل لدورة البيع والتحصيل والمرتجع والإقفال المحاسبي، وإلى مراجعة طريقة تسوية خصومات البيع وتكاليف التصنيع قبل التشغيل التجاري.


### دورة الموردين والفترات والجودة النهائية

- سندات صرف الموردين وتخصيصها على أوامر الشراء، مع منع تجاوز قيمة المقبول المستلم.
- مردودات المشتريات وتخفيض المخزون وحساب الموردين بقيد مزدوج.
- إقفال الفترات المحاسبية ومنع إنشاء القيود في فترة مغلقة.
- اعتماد جودة المنتج النهائي بعد التشغيل؛ يظل رصيد المنتج النهائي في حالة `PENDING_QC` ولا يسمح ببيعه أو استهلاكه قبل الإفراج.
- المرتجعات المقبولة مالياً تظل محجوزة للجودة حتى فحصها والإفراج عنها.

هذه الدورة ما زالت تحتاج إلى اختبارات تكامل سيناريوهات فعلية (خصوصاً المرتجع متعدد التشغيلات، تسويات أرصدة الموردين، وتزامن الإقفال مع الترحيل).


### التركيبات والتسويات والتقارير

- دورة التركيبة: مسودة ← مراجعة ← اعتماد، مع اشتراط مجموع مكونات 100%، ومنع تعديل التركيبة المعتمدة.
- تسويات المخزون بمسودة واعتماد، ومنع الرصيد السالب، وتسجيل حركات الجرد وقيد فروق المخزون.
- تقارير ميزان المراجعة، تقييم المخزون، تكلفة الإنتاج، وملخص المبيعات.
- تتبع جودة المخزون: مخزون خام مقبول، منتج نهائي محجوز حتى اجتياز الجودة، والمرتجعات تعود إلى حالة انتظار الفحص.

### حدود هذه النسخة

الموجود حالياً طبقة API وقاعدة بيانات واختبارات مصادقة وترحيل migrations على PostgreSQL 16. لا توجد بعد واجهات تشغيل Web/Windows كاملة، ولا اختبار تكامل شامل لكل دورة تجارية على قاعدة بيانات مملوءة ببيانات سيناريو، ولا اعتماد نشر إنتاجي. كما أن عكس المستندات بعد الترحيل ومطابقة الأستاذ العام وميزان المراجعة مع المستندات الفرعية لا تزال مطلوبة.


### عكس المستندات المرحلة

تمت إضافة مسارات عكس موثقة لفواتير البيع وسندات القبض وسندات صرف الموردين ومردودات المشتريات والمصروفات. العكس ينشئ قيداً عكسياً منفصلاً، ويحتفظ بالقيد الأصلي بحالة REVERSED، ويسجل السبب والمستخدم والتوقيت في سجل `document_reversals`. عكس فاتورة البيع ممنوع قبل عكس سندات القبض المرتبطة، وممنوع إذا كانت هناك مرتجعات غير مرفوضة. عكس المرتجع الشرائي يعيد الكميات إلى نفس رقم التشغيلة ويعيد حساب متوسط التكلفة.

كل عمليات العكس تخضع لقفل الفترة المحاسبية، ولا تحذف المستند الأصلي أو أثره.


### طلبات الشراء الداخلية

- إنشاء طلب شراء داخلي ببنود وكميات ومستودع وموعد احتياج.
- إرسال الطلب للاعتماد ثم موافقة مسؤول المشتريات.
- تحويل الطلب المعتمد إلى أمر شراء مرتبط بالمورد، مع تحديد سعر كل بند.
- منع التحويل قبل الاعتماد أو تكرار تحويل الطلب نفسه.


### Sales delivery and dispatch
- Create a delivery order from a posted sales invoice and reserve quantities against invoice lines.
- Prepare, mark ready, dispatch with driver/vehicle details, and confirm full or partial customer receipt.
- Prevent delivery planning beyond the invoice line quantity; cancelled pre-dispatch deliveries release their reserved quantities.
- API routes: `/api/v1/sales/deliveries`, `/:id/ready`, `/:id/dispatch`, `/:id/confirm-delivery`, and `/:id/cancel`.

راجع `docs/TEST_DEPLOYMENT.md` ثم شغّل PowerShell:
```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start-test.ps1
```
تستخدم الحزمة Docker Compose لتشغيل PostgreSQL 16 وواجهة Web/API، وتدعم النسخ الاحتياطي والاستعادة. لا تستخدمها على بيانات إنتاج.
